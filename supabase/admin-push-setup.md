# Notifications Android — عبد الحق فضلي

Les paiements (ajout ou modification effective) génèrent une alerte. Les absences génèrent une alerte à la troisième absence enregistrée successive, puis à la quatrième, cinquième et chaque absence supplémentaire. Une présence remet le compteur à zéro, les jours sans saisie ne comptent pas, et les dates futures sont ignorées. Un même nombre d'absences dans une série n'est pas notifié deux fois après un envoi accepté. Les présences, objectifs et enregistrements inchangés n'en génèrent pas. Aucun historique n'est envoyé à l'exécution de la migration. Le destinataire est contrôlé côté serveur : rôle `super_admin` et nom `عبد الحق فضلي` dans `teacher_profiles`.

## Mise en service

1. Après connexion du CLI au bon compte, exécuter `npm run push:setup -- --sync-gateway`. Les clés VAPID et le secret d'envoi sont générés localement dans `.env.push.local`. La clé JWT publique anonyme du projet est conservée dans `.env.gateway.local` pour franchir le contrôle JWT de la plateforme ; elle ne donne aucun droit administrateur. Le fichier `supabase/admin-push.local.sql` contient le schéma et la configuration Vault. Ces fichiers sont ignorés par Git : ne pas les publier. Une nouvelle exécution réutilise les mêmes clés.
2. Dans **le projet Supabase `szypbjvhwaiblnqqevbw`**, exécuter tout `supabase/admin-push.local.sql` dans le SQL Editor. Le script ajoute les tables d'abonnement/file d'attente, les déclencheurs et deux tâches Cron. Il ne modifie pas les données métier existantes. Réexécutable.
3. Connecter le CLI au compte qui possède ce projet : `npx supabase login` puis `npx supabase projects list`. Vérifier que `szypbjvhwaiblnqqevbw` figure dans la liste avant de continuer.
4. Configurer les secrets : `npx supabase secrets set --project-ref szypbjvhwaiblnqqevbw --env-file .env.push.local`.
5. Déployer : `npx supabase functions deploy admin-push --project-ref szypbjvhwaiblnqqevbw --yes`. La vérification JWT native de Supabase reste activée. Le JWT de l'utilisateur est aussi vérifié par la fonction avec `auth.getUser()`. Les appels de la base présentent le JWT public anonyme au contrôle de la plateforme et un secret d'envoi privé distinct à la fonction. Le JWT public seul ne permet aucun envoi.
6. Déployer le frontend habituel sur Cloudflare. Sur Android, ouvrir l'application dans Chrome, se connecter en tant que عبد الحق فضلي, appuyer sur la cloche puis **تفعيل الإشعارات على هذا الجهاز** et autoriser les notifications. L'autorisation doit être donnée sur le téléphone, jamais à distance.
7. Appuyer sur **إرسال إشعار تجريبي**, puis vérifier lors d'un paiement réel ou d'une troisième absence successive réelle. Aucun test ne doit créer de faux enregistrements en production.

## Fonctionnement et limites

- La réception ne dépend pas d'un onglet ouvert : un service worker reçoit les messages Web Push. Aucune donnée élève n'est mise en cache hors ligne.
- Les envois utilisent `Urgency: high` pour demander une livraison immédiate, y compris en arrière-plan. L'affichage dépend toujours d'Android, des restrictions de batterie/données et des autorisations de Chrome. Une fermeture normale ne doit pas être confondue avec « Forcer l'arrêt ».
- Le titre distingue absence/paiement et indique le nom de l'élève. Le corps inclut son professeur responsable si renseigné (propriétaire `students.created_by`), sans montant ni téléphone. Ces noms peuvent apparaître sur l'écran verrouillé. Ils sont figés à l'enregistrement de l'événement et restent dans la file privée au maximum 7 jours.
- Les nouvelles notifications d'absence et de paiement ouvrent directement `/students/<id>`. Si une connexion est nécessaire, cette destination est conservée après authentification. Pour une installation existante, appliquer `add-push-student-links.sql` et redéployer la fonction. Les alertes anciennes sans identifiant gardent leur destination générale. Recharger l'application une fois pour actualiser le service worker.
- Pour mettre à niveau une installation existante avec les noms et le seuil de trois absences, exécuter ensuite `add-admin-push-details-and-streak.sql`, puis redéployer la fonction. Cela ajoute des colonnes et une table privée de déduplication ; aucune donnée métier n'est modifiée. Les anciennes alertes de simple absence encore en attente ne sont plus envoyées. Une série reste dédupliquée même après nettoyage des événements, jusqu'à une nouvelle présence.
- Appliquer enfin `fix-admin-push-undelivered-streak.sql` et redéployer la fonction : une réservation de série n'est plus assimilée à un envoi accepté. `event_id` suit l'événement en cours et `delivered_at` n'est renseigné qu'après acceptation par le service Push. Sans appareil éligible, l'événement indique explicitement qu'aucun envoi n'a eu lieu. Une nouvelle saisie peut relancer une série non envoyée ; la fonction interne `enqueue_student_absence_push(student_id)` permet aussi de la réévaluer sans modifier les présences. Elle est réservée au serveur et ne rejoue que la série actuelle d'au moins 3 absences. Les séries déjà envoyées restent dédupliquées après nettoyage des événements.
- Pour la règle actuelle (alerte à 3, 4, 5...), appliquer ensuite `add-admin-push-each-absence.sql` puis redéployer la fonction. La table privée `admin_push_absence_steps` conserve une réservation par élève, dernière présence et nombre d'absences. Les réservations historiques sont conservées et les envois déjà acceptés ne sont pas répétés. Le compteur d'une nouvelle série repart de zéro après une présence. Cette migration ne déclenche aucun envoi rétroactif et ne modifie aucune présence.
- Le bouton d'arrêt concerne ce navigateur/appareil ; la déconnexion désabonne également ce navigateur. Plusieurs appareils peuvent être inscrits.
- Les abonnements et clés ne sont accessibles ni à `anon` ni à `authenticated` directement. Seule la fonction serveur y accède après validation du compte.
- Les notifications sont mises en file et expédiées immédiatement. Cron retente les envois échoués (jusqu'à 5 tentatives, messages âgés de moins de 24 h), avec bail de traitement et suivi par appareil. Les abonnements expirés (404/410) sont supprimés. Une interruption entre l'envoi et sa confirmation peut occasionnellement provoquer un doublon ; un tag stable permet au téléphone de remplacer la notification du même événement.
- Un incident de notification ne bloque pas l'enregistrement des absences/paiements. Les événements terminés ou anciens sont nettoyés après 7 jours.
- Vérifier `admin_push_events.last_error`, `attempts` et les logs de la fonction en cas d'échec. Une réponse HTTP du service Push confirme l'acceptation, pas l'affichage effectif sur le téléphone (permissions et restrictions Android restent applicables).
- Conserver les clés VAPID : leur rotation impose un nouvel abonnement sur chaque téléphone. Les secrets n'apparaissent jamais dans le frontend ou les logs.

## Vérifications locales

`npm run test:push` vérifie les déclencheurs PostgreSQL dans une base isolée, la limitation du destinataire, les droits d'accès, les baux de traitement et la navigation du service worker. `npm run build` et `npm run lint` vérifient le frontend. La fonction peut être vérifiée avec `deno check supabase/functions/admin-push/index.ts`.
